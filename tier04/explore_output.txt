A. Classical brute force: ask all 1024 inputs (comparison-only)
   queries: 1024, found s = 1100011000 in 8.0 s (512 colliding pairs)
   f takes 512 distinct values, exactly 2-to-1: True
   Sequential scan needs only 2^(top bit of s) + 1 queries here
   (top bit 9: 513 queries), but the worst case is 2^(n-1) + 1 = 513.

B. Classical birthday search: random inputs until two answers match
   one live run on Aer: 61 queries, 0.76 s
   3000 simulated runs: mean 40.1, median 38, max 122 queries (theory sqrt(pi x 1024 / 2) = 40)
   chance to have found s within a budget of q questions:
     q =   8:   2.7%
     q =  16:  10.5%
     q =  32:  39.2%
     q =  64:  87.3%
     q = 128: 100.0%

D. Simon under noise: depolarizing error after every cx
   183 cx gates in the circuit; two decoders per run: strict GF(2) solve versus majority vote
   p(cx)      strict     vote   (trials of 200 shots)
   0.0          100%     100%
   0.0001         0%     100%
   0.001          0%     100%
   0.003          0%     100%
   0.01           0%     100%
   0.03           0%     100%
   0.1            0%       0%
   Strict solving breaks at the first wrong y (one noisy equation can rule out
   the true s). Voting only needs the true s to win a majority of the runs.

E. Simon with the output register measured first (hint 1 version)
   60 runs, s recovered: True; every y.s = 0: True
   Same equations, same cost. Collapsing the output first only makes the picture
   easier to explain: the inputs hold x and x XOR s, and H turns that into y.s = 0.

F. Grover search for s (different algorithm, oracle used twice per round)
   f(0) = 231; 17 rounds, 35 oracle calls in one circuit (1 classical + 2/round)
   400 shots: P(s) = 0.50, P(0) = 0.50, most common non-zero = 1100011000 (s = 1100011000)
   7310 cx gates, depth 12095: about 39x bigger than Simon
   Quadratic speed-up only (about sqrt(2^n) rounds), so Simon's exponential win is lost.
